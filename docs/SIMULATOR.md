# Windows simulator

The target for this project is **webOS TV 23 Simulator for Windows (64-bit)**. Download and extract the **webOS TV 23** Windows archive from [LG's official Simulator Installation page](https://webostv.developer.lge.com/develop/tools/simulator-installation). LG currently lists `webOS_TV_23_Simulator_1.4.1_win.zip`. Keep the extracted simulator outside tracked source, or in the ignored `simulator/` directory. Select the executable inside the extracted archive; a newer platform simulator is a different test target.

Use Node.js 22 or newer and Windows PowerShell. Install this repository's dependencies with `npm ci`; QA uses the root `ws` dependency. Authorized decoder assets and LG's SDK JavaScript are separate local prerequisites for `npm run build`; see [SETUP.md](SETUP.md). Neither these scripts nor a clean source checkout supplies private recorder credentials or redistributable decoder binaries.

## Local configuration and build

Run `npm run configure`, then edit only the ignored `config.local.json`. Keep the complete configuration generated by that command. Set `development.simulatorExecutable` to the extracted Windows executable, and `development.simulatorDebugPort` to an unused local port. Paths can be absolute local paths or relative to this repository; UNC/network paths are refused.

Leave `development.simulatorServiceDirectory` empty to use the generic user-home location `.webos-instaon-viewer/service`. A configured value must be a dedicated directory outside the repository, with no symlinks or junctions. Prefer a location inside your user home: [LG's service-development instructions](https://webostv.developer.lge.com/develop/tools/simulator-dev-guide) require services to be under the user's home directory.

The same local config supplies `recorder`, `cloud`, `viewer.cameraCount`, and `viewer.defaultView` to the build. Configure `development.decoderAssetsDirectory`, and either `development.webosSdkScript` or `development.webosCliDirectory`, for the build prerequisites. The launcher does not run SDK setup scripts or device tools. `television` settings have no role in simulator launch or QA; keep `television.enabled` false for simulator-only work.

```powershell
npm run build
npm run simulator -- --check
```

The check validates configuration, staged metadata, required files, paths, and the configured executable. It does not launch a process, copy files, test a network endpoint, or inspect generated credential contents. It does not check whether the debug port is free.

The build must produce:

```text
build/direct/app/                 app ID: org.webos.instaonviewer
build/direct/service/             service ID: org.webos.instaonviewer.service
  credentials.private.json        generated from config.local.json
```

These are ignored private outputs. Do not publish the build, runtime copies, simulator profiles, or reports.

## Launch and register the service

Run this section only when you intend to start the simulator. Starting the app and enabling its service can connect to the recorder/cloud configured in `config.local.json`.

```powershell
npm run simulator -- --debug
```

The Node runner loads the single local configuration and passes only development settings to `tools/launch-simulator.ps1` over standard input. The PowerShell launcher copies the staged service, including its generated private configuration, into a fresh `session-<random ID>` directory under the configured service directory. It launches the configured executable with this repository's staged app, an isolated profile under ignored `build/simulator/`, and a unique launch-session marker. Existing service directories and simulator processes are left alone.

Each fresh profile needs its own service registration:

1. Use **File > Add Service** (or **Service** on the simulator remote).
2. Select the fresh service directory printed by the launcher, containing `package.json`.
3. Open **Tools > Service List** and enable `org.webos.instaonviewer.service`.
4. If needed, reopen the app using **File > Launch App** and select `build/direct/app`. For automated QA, preserve the original launch parameters: if manually reopening loses the session marker, close this simulator and launch again through the command above, then register the new runtime.

Without `--debug`, the app still launches, but QA cannot connect. Debug mode binds CDP to `127.0.0.1` on `development.simulatorDebugPort`. The launcher first tests whether that loopback port is free and refuses an occupied port. It never terminates another simulator or takes over its debug endpoint. If an older simulator occupies the configured port, close that instance yourself or choose a different port in `config.local.json`, then launch this repository. There is no remote CDP host option.

The launcher does not discover, inspect, install on, or contact a physical TV. It does not invoke device CLI commands, SSH, TV discovery, or private-key tools. Only the configured local simulator executable is started. The service itself uses the configured recorder/cloud connection when enabled.

## QA of this repository's simulator

After launching with `--debug`, enabling the service, and allowing initial feeds to load:

```powershell
npm run qa:simulator
npm run qa:simulator -- --soak-seconds 60 --timeout-seconds 180
# Optional: deliberately lose one WebGL context and test recovery.
npm run qa:simulator -- --gpu
# Verify the UI without registering the service or opening camera feeds.
npm run qa:simulator -- --ui-only
```

The default soak is 15 seconds; accepted values are 1–3600 seconds. Each readiness condition has a 120-second timeout by default, adjustable to 1–300 seconds. Cold cloud handshakes may take over a minute. The optional GPU test requires `WEBGL_lose_context` support and deliberately interrupts a renderer in this simulator.

QA requires the launch record in ignored `build/simulator/session.json`, the exact staged `build/direct/app/index.html` page, and the matching `webOSSystem.launchParams.simulatorSession` marker. It refuses unrelated pages, ambiguous matches, stale launch sessions, external WebSocket URLs, other ports, and HTTP redirects. Every evaluated action rechecks page/session identity, including cleanup. It never automatically launches a simulator.

Live checks cover configured active cameras, 4/8/10/16-tile layouts, enlargement and Escape/Back behavior, 4:3 aspect and centering, viewport overflow, pause closing recorder connections, resume, ongoing fresh frames, and the 192 MiB shared WASM heap budget. `--ui-only` checks the controls, layouts, enlargement/Back behavior, profile control, and viewport overflow without service registration or camera feeds. Counts come from the configured camera count and selected view. QA does change the running simulator UI; live mode can reopen recorder connections when resuming feeds.

Successful runs write a uniquely named JSON report only to ignored `reports/`. Reports contain numeric frame/memory/layout measurements and sanitized check results; they omit recorder credentials, connection URLs, raw service responses, and HTML. Failures print a concise error and exit nonzero. Ctrl+C or socket failures reject pending requests, clear their timers and close or terminate the owned CDP socket within a bounded interval; the simulator stays running.

For offline syntax checks that do not read local configuration or start the simulator:

```powershell
node --check tools/simulator.cjs
node --check tools/simulator-qa.cjs
$parseErrors = $null
[System.Management.Automation.Language.Parser]::ParseFile((Join-Path $PWD 'tools/launch-simulator.ps1'), [ref]$null, [ref]$parseErrors) | Out-Null
if ($parseErrors.Count) { throw 'Simulator launcher has PowerShell syntax errors.' }
```

## Troubleshooting and cleanup

- Missing files or mismatched IDs: rerun `npm run build` in this repository, then `npm run simulator -- --check`. Do not substitute another workspace's private build.
- No matching owned session: launch through `npm run simulator -- --debug` and keep that app open. A page opened manually without the unique marker is intentionally refused.
- Feeds remain at Connecting: check the simulator's service list, the exact fresh runtime directory, authorized decoder assets, and local config. No recorder credentials should be placed in source, terminal commands, or reports.
- Service does not register: select the directory containing its `package.json`, preferably under your user home. Register each fresh runtime in its fresh profile. LG's simulator has a different service environment from a TV.
- Debug port occupied: the helper does not close the occupying process. Close your old instance or edit the configured port; QA and launcher use the same config value.
- Cleanup: close the owned simulator, remove its service registration in that profile if necessary, then manually remove only the specific generated `session-<ID>` service copy and corresponding ignored `profile-<ID>` directory you no longer need. These copies contain private configuration. Neither tool deletes runtimes or older private builds automatically.

LG documents [simulator limitations](https://webostv.developer.lge.com/develop/tools/simulator-introduction), including differences from real-device media behavior. A simulator pass verifies these desktop checks; it does not establish physical-TV performance, end-to-end latency, capture synchronization, or deployment results.
